# Fase 7.1 — Fuente de datos de alimentos

**Decisión: 29 de septiembre de 2026.** Este documento conserva la decisión y los criterios iniciales de 7.1; las fases 7.2–7.4 se implementaron después, con un recorte menor y las salvedades de «Estado de implementación» abajo. El criterio de [PLAN.md §2 y §7](../PLAN.md) es que los datos curados viajen con la app y no dependan de una API durante el uso.

### Reproducción y mantenimiento del recorte actual

Los 43 códigos, revisiones, hashes SHA-256 de la respuesta cruda, fechas y notas están fijados en [`scripts/foods/whitelist.json`](../scripts/foods/whitelist.json); las respuestas seleccionadas comprimidas viven en `scripts/foods/snapshots/`. Sin red y sin escribir:

```bash
node scripts/food-import.mjs --check
node --test scripts/food-catalog.node-test.mjs
```

`node scripts/food-import.mjs` regenera de forma determinista el catálogo, la atribución y las copias públicas desde esos snapshots, **no** desde la API. Para revisar una actualización, `node scripts/food-fetch.mjs --refresh` consulta solo la lista blanca y deja respuestas nuevas en `scripts/foods/staged/`; **no** reemplaza el snapshot fijado. Tras comprobar producto/variante y valor nutricional con evidencia, `node scripts/food-promote.mjs` exige versión mayor, nota, energía/base explícitas y promueve una ficha; ver [uso exacto](../scripts/foods/README.md). El fetch usa un User-Agent identificable y 4,5 s entre lecturas, por debajo del límite OFF de 15 lecturas de producto/min/IP. La app no consulta la API OFF al usar el catálogo. El catálogo abierto y su atribución se ofrecen como `/data/foods-catalog.json` y `/data/foods-catalog-attribution.json` **en el build desplegado**; hoy Vercel Authentication redirige a SSO antes de entregarlos a visitantes anónimos. El diario privado no forma parte de esa descarga.

## Decisión concreta y límite

**Elegir OFF como única fuente externa del primer catálogo, limitado a ~80–120 productos envasados/comercializados en Argentina y revisados manualmente.** Se prioriza reconocer lo que la persona realmente compra aquí sobre tener el mejor perfil analítico de alimentos genéricos. La licencia más exigente se acepta **solo** porque el recorte y su atribución se publicarán como datos abiertos separados del código y de los registros privados. No combinar registros OFF con FDC en una misma base derivada ni presentar productos envasados como equivalentes de frutas, carnes o platos caseros. FDC queda descartada para este primer recorte, no declarada inferior en calidad nutricional.

Este MVP **no promete cobertura total de la dieta**: quedan fuera recetas, alimentos frescos sin ficha apta, escáner universal, fotos de envases, recomendaciones nutricionales y objetivos de macronutrientes. Si la auditoría de 7.2 no encuentra una selección local suficiente con energía verificable, se reduce el catálogo o se reabre esta decisión; no se rellenan calorías por conjetura. Cada ficha debería identificar producto y variante exacta, no solo marca. La UI debe decir que son valores orientativos de etiqueta y que la etiqueta actual del envase prevalece ante diferencias.

### Contrato para 7.2: catálogo pequeño, versionado y offline

- Lista blanca manual de códigos de barras/IDs OFF, con nombre visible en español y alias de búsqueda. Organizarla por grupos cotidianos (lácteos, cereales/panes, bebidas, snacks, conservas, etc.) **sin cuotas automáticas**; revisar duplicados, variantes de sabor/tamaño y productos descontinuados.
- Aceptar únicamente ficha con nombre, marca, país de venta Argentina, energía no nula y unidad de base inequívoca. Revisar foto de tabla nutricional o fuente del fabricante cuando esté disponible; documentar revisión manual y descartar valores obviamente imposibles o inconsistentes con la declaración nutricional. No inferir kcal desde macros como sustituto silencioso ni interpretar campo faltante como cero.
- JSON compacto versionado dentro del bundle estático, sin solicitud de red en tiempo de uso, como `src/features/exercises/catalog.json`. Presupuestar el peso real del JSON y del precache antes de cerrar 7.2; no incluir fotos ni el dump. El catálogo y sus cambios deben ser descargables en formato legible por máquina bajo ODbL, con atribución visible **«Datos de productos: Open Food Facts (ODbL 1.0)»** y enlace a fuente/licencia en la app y documentación. Mantener los registros de usuario en tablas con RLS, separados del catálogo abierto.
- Por fila conservar al menos `catalogVersion`, `source=OFF`, `sourceCode` (string para preservar ceros), `sourceRevision`, `sourceUrl`, `sourceRetrievedAt`, `sourceExportHash` o hash de respuesta cruda, `reviewedAt`, `reviewNote`, `energyKcalPer100`, `basisUnit` (`g`/`ml`), `name`, `brand` y `countriesTags`. No almacenar imágenes sin evaluar la licencia separada. Si una corrección cambia kcal, crear nueva versión de catálogo: los registros históricos retienen `catalogVersion`, cantidad y **kcal/100 y kcal calculadas al momento de registrar** para que no cambie el pasado.

### Contrato para 7.3: cantidades

La cantidad canónica será **gramos** para sólidos y **mililitros** para líquidos cuya ficha OFF esté expresada por 100 ml. Calorías de una entrada = `cantidad × kcalPor100 / 100`, redondeadas para presentación; conservar la precisión decimal para el total. Una «porción» o «unidad» será solo un atajo si tiene **peso/volumen numérico explícito y revisado para ese producto**; no asumir que una porción de la etiqueta equivale a 100 g, ni convertir ml a g sin densidad. Permitir cantidad manual positiva; rechazar cero, negativos y cantidades absurdas con validación. Mostrar siempre la unidad y la base nutricional. El diario es por fecha local del usuario, no UTC.

### Contrato para 7.4: cierre contra el objetivo

Comparar **kcal ingeridas del día** con `energyReport().target.kcal` de [Fase 5.4](../PLAN.md) cuando el perfil esté completo. Ese objetivo ya incorpora TDEE estimado de sesiones de 28 días, meta −500/+300/mantenimiento, redondeo a 50 y piso BMR: **no volver a sumar/restar las calorías del entrenamiento**. Guardar un snapshot diario de objetivo y TDEE al primer registro/cierre para que el historial no se reescriba si luego cambian peso, perfil o sesiones. Sin objetivo listo, permitir registrar comida pero mostrar «sin objetivo calculable», no saldo ficticio. El saldo indica diferencia respecto de una estimación, no «calorías ganadas/perdidas» ni compensación que deba comerse. **No autoajustar el objetivo por la evolución real del peso**; solo cambia por los datos que ya alimentan `energyReport()` o por una futura decisión explícita revisada con criterios de seguridad.

## Importación reproducible para 7.2

1. Seleccionar manualmente los ~80–120 códigos y registrar revisión nutricional. Para esta escala, adquirir **solo fichas elegidas** una vez mediante la API de producto OFF, no descargar los dumps gigabyte ni consultar en runtime. Respetar su [límite de 15 lecturas de producto/min/IP y User-Agent identificable](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/). El uso puntual de API para construir un **snapshot descargable dentro de F1t** no cambia la decisión de «sin API en vivo».
2. Fijar por código la [revisión OFF](https://support.openfoodfacts.org/help/en-gb/12-api-data-reuse/105-how-can-i-access-historical-data) y archivar las respuestas crudas de **solo** las fichas seleccionadas con SHA-256; no depender de que el export diario siga igual (OFF no ofrece dumps históricos). Documentar fecha, URL, revisión, hash y versión del importador. Al regenerar, leer el snapshot fijado; una actualización upstream es una revisión explícita de lista blanca + nutrición, no una descarga invisible.
3. Normalizar exclusivamente kcal y base 100 g/100 ml, producir salida ordenada determinísticamente y validar unicidad de códigos, campos requeridos, números finitos/no negativos, fuente, unidad, revisión y correspondencia con snapshots. Hacer fallar el importador ante datos faltantes o cambio de esquema, en vez de publicar un catálogo parcialmente roto. Probar determinismo comparando hashes de dos generaciones con la misma entrada.
4. Antes de distribuir, confirmar con asesoramiento/licencia de OFF que la publicación del recorte, la atribución y la separación de diarios privados cumplen ODbL; es el **requisito externo pendiente**, no una exención inferida por F1t. También volver a medir cobertura argentina sobre la lista blanca una vez se restablezca el acceso a OFF. Si no se puede cumplir la obligación de compartir el catálogo derivado, **no publicar OFF**: reabrir la fuente (FDC CC0 sería la alternativa para un catálogo genérico, con menor cobertura local).
